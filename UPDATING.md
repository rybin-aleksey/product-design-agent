# Шаблон агента: как заводить продукты и обновлять их

Этот репозиторий — **шаблон** агента продуктового дизайна. Для каждого продукта делается своя копия шаблона, а улучшения агента передаются между шаблоном и копиями через git.

```text
                ┌──────────────────────────┐
                │      Шаблон агента       │   rybin-aleksey/product-design-agent
                │  теги версий: v1.0.0 …   │
                └───────┬──────────▲───────┘
   обновление продукта  │          │  перенос улучшения
   (git merge)          │          │  (git cherry-pick)
            ┌───────────▼──┐   ┌───┴──────────┐
            │  Продукт A   │   │  Продукт B   │   …
            └──────────────┘   └──────────────┘
```

Обновления не рассылаются автоматически. Пуш в продукт меняет только этот продукт. Изменение попадает в другие продукты, только когда его перенесли в шаблон, а каждый продукт сам забрал обновление.

---

## 1. Главное правило: файлы шаблона и файлы продукта

| Файлы шаблона (приходят из шаблона) | Файлы продукта (живут только в копии) |
|---|---|
| `AGENTS.md`, `CLAUDE.md`, `README.md` | `workspace/product/context/` |
| `UPDATING.md`, `CHANGELOG.md`, `.gitattributes` | `workspace/product/project.md` |
| `skills/`, `workflows/`, `knowledge/` | `workspace/product/tasks/` |
| `.agents/`, `.claude/` | `workspace/product/ds/` |

- Работа над продуктом меняет **только** `workspace/product/`.
- Если в продукте понадобилось улучшить сам агент (скилл, workflow, инструкцию), это делается **отдельным коммитом**, который не трогает `workspace/`. Только такой коммит можно чисто перенести в шаблон.
- Не смешивайте в одном коммите правку агента и работу над продуктом.

Если правило соблюдается, обновление продукта из шаблона проходит без конфликтов.

---

## 2. Завести новый продукт

```bash
# 1. Клонировать шаблон
git clone https://github.com/rybin-aleksey/product-design-agent.git my-product
cd my-product

# 2. Шаблон становится вторым удалённым репозиторием «template»
git remote rename origin template

# 3. Подключить пустой репозиторий продукта (создать его заранее на GitHub, без README)
git remote add origin https://github.com/<аккаунт>/my-product.git
git push -u origin main

# 4. Один раз в этой копии: включить правило «данные продукта не перезаписываются»
git config merge.ours.driver true
```

Дальше заполните `workspace/product/` (контекст, задачи) и работайте с агентом как обычно.

> Используйте именно `git clone`, а не кнопку GitHub «Use this template». Кнопка создаёт репозиторий без общей истории с шаблоном, и обновления потом сливаются с трудом.

> Шаг 4 нужно повторять в каждой новой копии репозитория продукта, в том числе после `git clone` продукта на другом компьютере. Настройка хранится локально и не передаётся через git.

## 3. Сценарий 1. Обновить продукт до новой версии шаблона

```bash
# 1. Узнать, что нового в шаблоне
git fetch template --tags
git tag --list "v*"                           # доступные версии
git log --oneline main..template/main         # какие изменения ещё не в продукте

# 2. Прочитать CHANGELOG новой версии: нет ли раздела «Что сделать в продукте»
git show template/main:CHANGELOG.md

# 3. Обновиться
git merge v1.3.0                              # до конкретной версии (рекомендуется)
# или
git merge template/main                       # до самой свежей

# 4. Отправить обновлённый продукт
git push
```

Какая версия шаблона сейчас стоит в продукте:

```bash
git describe --tags --abbrev=0
```

Если версия вышла с ручными шагами (раздел «Что сделать в продукте» в `CHANGELOG.md`), выполните их сразу после `merge` и закоммитьте.

### Если случился конфликт

Конфликт значит, что один и тот же файл шаблона поменяли и в шаблоне, и в продукте.

```bash
git status                     # список файлов с конфликтом
# открыть файл, оставить нужный вариант, удалить маркеры <<<<<<< ======= >>>>>>>
git add <файл>
git commit                     # завершить слияние
```

Передумали обновляться — `git merge --abort` вернёт всё как было.

После разрешения конфликта подумайте, не стоит ли перенести вашу правку в шаблон (сценарий 2): тогда в следующий раз конфликта не будет.

---

## 4. Сценарий 2. Перенести улучшение из продукта в шаблон

### Шаг 1. В продукте: отдельный коммит с правкой агента

```bash
git add skills/new-skill/                                 # только файлы шаблона
git commit -m "skill(new-skill): добавить скилл ..."
git push
git log --oneline -1                                      # запомнить хеш коммита
```

В коммите не должно быть файлов из `workspace/`. Проверить: `git show --stat <хеш>`.

### Шаг 2. В шаблоне: забрать коммит

Нужна локальная копия шаблона (один раз: `git clone https://github.com/rybin-aleksey/product-design-agent.git`).

```bash
cd product-design-agent                                   # копия шаблона
git pull

# один раз: подключить продукт как источник
git remote add my-product https://github.com/<аккаунт>/my-product.git
# (можно и локальный путь: git remote add my-product ../my-product)

git fetch my-product
git cherry-pick <хеш-коммита>                             # перенести только этот коммит
```

### Шаг 3. В шаблоне: выпустить версию

1. Допишите в `CHANGELOG.md` новую версию: что добавилось и нужно ли что-то сделать в продукте.
2. Закоммитьте, поставьте тег и отправьте:

```bash
git add CHANGELOG.md
git commit -m "release: v1.3.0"
git tag v1.3.0
git push origin main --tags
```

### Шаг 4. В остальных продуктах

Обновитесь по сценарию 1. Продукт, из которого пришла правка, тоже обновляется: git увидит, что изменение уже есть, и конфликта не будет.

---

## 5. Улучшение прямо в шаблоне

Если правка агента не связана с конкретным продуктом, делайте её сразу в копии шаблона: коммит → запись в `CHANGELOG.md` → тег → `git push origin main --tags`. Продукты получают её по сценарию 1.

---

## 6. Как нумеровать версии

`vMAJOR.MINOR.PATCH`:

| Что поменялось | Пример | Версия |
|---|---|---|
| Исправления текста, мелкие правки | уточнили формулировку в чек-листе | `v1.2.0 → v1.2.1` |
| Новый скилл, workflow, знание | добавили `design-system-scan` | `v1.2.1 → v1.3.0` |
| Меняется структура папок или нужны ручные шаги в продукте | скилл стал сохранять файлы в другое место | `v1.3.0 → v2.0.0` |

## 7. Шпаргалка

| Задача | Где | Команды |
|---|---|---|
| Новый продукт | — | `git clone <шаблон> my-product` → `git remote rename origin template` → `git remote add origin <продукт>` → `git push -u origin main` → `git config merge.ours.driver true` |
| Что нового в шаблоне | продукт | `git fetch template --tags` → `git log --oneline main..template/main` |
| Обновить продукт | продукт | `git merge vX.Y.Z` → `git push` |
| Текущая версия шаблона | продукт | `git describe --tags --abbrev=0` |
| Отменить неудачное слияние | продукт | `git merge --abort` |
| Перенести правку в шаблон | шаблон | `git fetch my-product` → `git cherry-pick <хеш>` → `CHANGELOG.md` → `git tag vX.Y.Z` → `git push origin main --tags` |

---

## 8. Ограничения

- Правило `.gitattributes` (`workspace/** merge=ours`) защищает данные продукта, только если файл изменён и в шаблоне, и в продукте. Если шаблон **удалил** файл-заготовку, который продукт заполнил, git всё равно покажет конфликт: оставьте версию продукта (`git add <файл>`).
- Без `git config merge.ours.driver true` правило из `.gitattributes` не работает, и конфликты в `workspace/` разрешаются вручную.
- Заготовку `workspace/product/` в шаблоне лучше менять как можно реже.
