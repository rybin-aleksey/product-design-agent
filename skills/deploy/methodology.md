# Методология: публикация и деплой

`code/` — `workspace/product/code/`, `project.md` — `workspace/product/project.md`.
Self-check — в [checklist.md](checklist.md); тексты для пользователя и конфиги — в [output-template.md](output-template.md).

## Фаза 0. Путь и общая подготовка

1. Есть раздел «Публикация» в `project.md` — повторный запуск: путь и адрес уже известны, переходи к обновлению (раздел «Повторный запуск»).
2. Спроси: **куда публикуем — на сервис (Vercel / Netlify / Cloudflare Pages) или на свой сервер?** Если пользователь не знает — рекомендуй сервис (Vercel): HTTPS и авто-обновление из коробки.
3. Общая подготовка в `code/`:
   - `npm run build` — без ошибок, на выходе `dist/`. Ошибки сборки чинятся до публикации.
   - `vite.config`: `base: '/'` (публикация из корня домена или порта).
   - `.gitignore`: `node_modules/`, `dist/`, `.env`, `.env.*`, `!.env.example`.
   - Секретов в коде нет (поиск `ghp_`, `sk-`, `AKIA`, `-----BEGIN`, `.env`); переменные окружения, если нужны, — `VITE_*` только с несекретными значениями (всё `VITE_*` попадает в бандл).
   - Роутер: на hash-роутере fallback не обязателен, но конфиг всё равно добавляется — безвредно и на случай смены роутера.
4. Предложи `<meta name="robots" content="noindex">` в `index.html`, чтобы прототип не индексировался поисковиками (по согласию).
5. Предупреди: публичная ссылка открывается любым, у кого она есть; данные в прототипе — демо.

## Путь A — сервис

### A1. Актуальный репозиторий

- Репозиторий — из раздела «Репозиторий разработки» в `project.md`. Нет — сначала [github-handoff](../github-handoff/SKILL.md) (заливка `workspace/product/code/`).
- Сравни: в репозитории актуальный прототип или только база с первой передачи? Устарел — обнови по [github-handoff](../github-handoff/methodology.md) фаза 5, в `main`, одним пушем, теми же правилами про токен и `.gitignore`.
- Если в репозиторий залит весь проект продукта, а не только `code/` — в настройках сервиса **Root Directory** = `workspace/product/code`.

### A2. Конфиг fallback и подключение

1. Конфиг SPA-fallback (шаблоны в [output-template.md](output-template.md)):
   - Vercel — `code/vercel.json` с rewrite всех путей на `/index.html`;
   - Netlify — `code/public/_redirects` со строкой `/* /index.html 200` (именно в `public/`: Vite копирует его в `dist/`);
   - Cloudflare Pages — тот же `public/_redirects` (без `404.html` Pages и так отдаёт SPA, файл фиксирует поведение явно).
   Закоммить и запушь тем же способом, что в A1.
2. Выведи пользователю браузерные шаги выбранного сервиса ([output-template.md](output-template.md)). Настройки сборки: Framework — Vite, Build command — `npm run build`, Output — `dist`, Root Directory — по A1.
3. Дождись, пока пользователь пришлёт ссылку на проект в сервисе или сообщит об ошибке сборки (лог сборки — попроси скопировать текст ошибки).

### A3. Публичность и проверка

1. **Vercel:** открой ссылку в приватном окне (или попроси пользователя). Просит вход в Vercel — включена Deployment Protection: Settings → Deployment Protection → Vercel Authentication → выключить → Save. Netlify и Cloudflare Pages публичны по умолчанию.
2. **Стабильная ссылка** — Production Domain проекта (`<project>.vercel.app`, `<site>.netlify.app`, `<project>.pages.dev`), а не URL конкретного деплоя с хешем.
3. Проверка: главная, затем **прямой переход** на внутренний роут (вставить URL в новую вкладку) и обновление страницы на нём — не 404. Проверку делай разовым `curl -sI <url>/<route>` (200) и в браузере. **Не опрашивай живой URL в цикле**: Vercel примет это за бота и включит Security Checkpoint (403 для всех). Готовность деплоя — по коммит-статусу на GitHub.
   Vercel не собирает коммит, если email автора не привязан к GitHub-аккаунту: коммитить email'ом аккаунта (часто `…@users.noreply.github.com`).
4. Расскажи про авто-пересборку: каждый пуш в `main` пересобирает сайт за 2–3 минуты. Пока идёт работа — смотреть локально (`npm run dev`), живую версию обновлять пушем, когда устраивает.

## Путь B — свой VPS

### B1. Доступ и разведка

1. Запроси **IP** и **пользователя** (обычно `root`). Способ входа, по приоритету:
   1. **SSH-ключ уже работает:** `ssh -o BatchMode=yes -o ConnectTimeout=10 root@<IP> true` — успех, пароль не нужен.
   2. **Добавить ключ** (пароль не проходит через чат): если нет `~/.ssh/id_ed25519` — с согласия `ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519`. Пользователь добавляет публичный ключ в панели провайдера (раздел SSH keys) или сам выполняет одну команду в своём терминале и вводит пароль (команда в [output-template.md](output-template.md)).
   3. **Пароль в чат** — крайний вариант: нужен неинтерактивный клиент (`sshpass` или Python `paramiko` во временном окружении в scratchpad). Пароль только в окружении команды, не в файлах; после деплоя — рекомендация сменить пароль и перейти на ключ.
2. **Разведка read-only** одним подключением: ОС (`cat /etc/os-release`), занятые порты (`ss -tlnp`), есть ли nginx и его сайты (`nginx -v`, `ls /etc/nginx/sites-enabled /etc/nginx/conf.d`), статус firewall (`ufw status`), свободное место (`df -h /`).
3. **Порт:** 80, если свободен и не используется VPN / другим веб-сервером; иначе свободный из 8080, 8081, 3000. Порт VPN (часто 443 или кастомный) не трогать.
4. **План** пользователю и подтверждение (шаблон в [output-template.md](output-template.md)): что ставим (nginx — если нет), порт, каталог `/var/www/<app>`, новый файл конфига, правило firewall.

### B2. Заливка и отдача

1. `npm run build` в `code/` — свежий `dist/`.
2. nginx: нет — `apt-get update && apt-get install -y nginx` (Debian / Ubuntu; для других ОС — их пакетный менеджер). Существующие конфиги и сайты **не правятся**; дефолтный сайт на 80 отключается, только если порт 80 выбран под прототип и сайт — дефолтная заглушка nginx (`/etc/nginx/sites-enabled/default`), с подтверждением.
3. Конфиг `/etc/nginx/sites-available/<app>` (шаблон в [output-template.md](output-template.md)) со `try_files $uri /index.html;`, ссылка в `sites-enabled`, `nginx -t` → только при успехе `systemctl reload nginx`.
4. Заливка `dist` без `node_modules` и исходников, с заменой старой версии целиком:
   ```bash
   tar -C dist -czf - . | ssh root@<IP> 'set -e; rm -rf /var/www/<app>.new; mkdir -p /var/www/<app>.new; tar -xzf - -C /var/www/<app>.new; rm -rf /var/www/<app>.old; [ -d /var/www/<app> ] && mv /var/www/<app> /var/www/<app>.old; mv /var/www/<app>.new /var/www/<app>; rm -rf /var/www/<app>.old'
   ```
5. Firewall:
   - `ufw` **активен** → `ufw allow <порт>/tcp`;
   - `ufw` **неактивен** → ничего не включать (включение может отрезать VPN и SSH);
   - попроси пользователя проверить firewall в панели провайдера (если есть) и открыть порт там.
6. Проверка, что VPN жив: сервис VPN и его порт на месте (`ss -tlnp` — тот же список плюс новый порт).

### B3. Проверка и оговорки

1. `curl -sI http://<IP>:<порт>/` и `curl -sI http://<IP>:<порт>/<внутренний-роут>` — 200; открыть в браузере, обновить страницу на внутреннем экране.
2. Оговорки пользователю: адрес по `http` — браузер пишет «не защищено», для теста нормально; secure-context функции (камера, геолокация, буфер обмена) по голому IP не работают; домен и HTTPS — отдельная задача.

## Повторный запуск = обновление

- **Путь A:** `npm run build` локально (проверка), обновить репозиторий через github-handoff (фаза 5) в `main` — сервис пересоберёт сам; через 2–3 минуты проверить роуты по стабильной ссылке. Незаконченная итерация — в отдельную ветку: сервис создаст preview-ссылку, production не изменится.
- **Путь B:** `npm run build`, заливка командой из B2 (атомарная замена), проверка роутов. nginx и firewall не трогаются, если порт и каталог те же.
- Обновить «Последнее обновление» в `project.md`. В итоге — что обновлено.
