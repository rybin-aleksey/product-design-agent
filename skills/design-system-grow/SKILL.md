# Расширение UI-кита (grow_ui_kit)

## Назначение

Добавить в существующую ДС недостающие компоненты, привязанные к тем же Variables и TextStyles, что и стартовый набор:
каталог → выбор компонентов → md-описания (апрув) → пакетная отрисовка в Figma → запись в `components.md` → аудит.
Один прогон, тот же Figma-файл, одна новая секция «UI Kit — extended».

## Когда использовать

- Запускается из ветки «Расширение UI-кита» в [workflows/design-task](../../workflows/design-task/README.md).
- Пользователь просит «добавить в ДС таблицу / табы / тосты», «расширить UI-кит», «не хватает компонентов».
- Существуют `workspace/product/ds/CONTRACT.md` и непустой `workspace/product/ds/components.md` (после [design-system-from-0](../design-system-from-0/SKILL.md) или [design-system-scan](../design-system-scan/SKILL.md)).

**Не использовать:**
- Если ДС нет или `components.md` пуст — сначала `design-system-from-0` или `design-system-scan`.
- Если источник ДС — **корпоративная** (см. `ds/source.md` и `ds/CONTRACT.md`): её файл править нельзя, недостающее оформляется локальным паттерном в `ds/patterns.md` по контракту.
- Для расширения матрицы вариантов и состояний (hover / focus / disabled / loading) у существующих компонентов — нужен [design-system-variants](../design-system-variants/SKILL.md).

## Роль

Дизайн-системный архитектор с опытом расширения UI-китов. Знает, какие компоненты пора заводить в ДС, а какие достаточно собрать композицией существующих. Проверяет каталог перед заведением нового, чтобы не плодить дубликаты.

Адаптация роли под продукт (по `ds/brand-brief.md` или `workspace/product/context/`):

| Продукт | Фокус |
|---|---|
| B2C веб | Формы заказа, карточки товара, модальные окна подтверждения |
| B2B SaaS | Дашборды, сложные таблицы, фильтры, контекстные меню |
| Мобильное приложение | Тач-таргеты, тонкая работа с Toast и Sheet |
| Лендинг | Hero-секции, accordion, sticky-CTA |

## Входные данные

- `ds/CONTRACT.md`, `ds/foundation.md`, `ds/components.md` (читаются целиком по правилу `AGENTS.md`), при наличии `ds/source.md` и `ds/brand-brief.md`.
- Папка задачи `workspace/product/tasks/<TASK-ID>/` — для черновика описаний и рабочих заметок.
- Ссылка на тот же Figma Design-файл, где лежит секция «Foundation» (или ДС после ds_scan), если её нет в `CONTRACT.md` / `source.md`.

## Фазы

| Фаза | Что делаем | Результат | Гейт |
|---|---|---|---|
| 1. Каталог и выбор | Чтение `components.md`, список типовых пробелов, чек на дубликаты | Зафиксированный набор компонентов | Пользователь подтвердил набор |
| 2. Описания | md-описание каждого компонента по шаблону | `analysis/grow-ui-kit-draft.md` | **Апрув по каждому компоненту** |
| 3. Figma | Секция «UI Kit — extended», пакеты по 2–3 компонента + проверочные чтения | Компоненты в Figma | Проверка по факту пройдена для каждого пакета |
| 4. Каталог и аудит | Дописать `components.md`, один аудит-вызов, финальный показ | Обновлённый `ds/components.md`, отчёт аудита | Аудит без открытых расхождений |

Подробности каждой фазы, код и правила отрисовки — в [methodology.md](methodology.md).
Гейты и проверки — в [checklist.md](checklist.md).
Шаблоны описаний и отчётов — в [output-template.md](output-template.md).

## Жёсткие правила

1. **Никаких MCP-вызовов до апрува md-описаний.** Текстовые правки бесплатны, перерисовка пакета — нет.
2. **Чек на дубликаты перед заведением.** Если близкий компонент уже есть — расширяем его варианты отдельной задачей, а не заводим близнеца.
3. **Минимальная матрица вариантов:** 2–3 варианта на компонент. Большие матрицы ломают write-tools.
4. **Только `use_figma`.** Перед первым вызовом загрузи скилл `figma-use`; для Figma MCP сначала `create_session` с `fileKey`.
5. **Компоненты — настоящие `ComponentNode` / `ComponentSet`**, не фреймы.
6. **Типографика — только существующие TextStyles ДС.** Новые TextStyles не создаются; прибитые `fontSize` / `fontName` запрещены.
7. **Fills, strokes, радиусы, отступы — только через Variables.** Прибитые hex и не-токенные числа запрещены (инвариант `ds/CONTRACT.md`).
8. **Auto Layout везде.**
9. **Пакеты по 2–3 компонента** на один мутирующий вызов, после каждого — отдельный read-only вызов проверки.
10. **Никакого `throw` в конце мутирующего вызова**: он откатывает всю транзакцию.
11. **Имена латиницей:** ComponentSet — `Table`, `Tabs`, `Toast`; варианты — `Property=value`.
12. **Аудит обязателен.** Без него прогон не завершён.

## Где сохранять

```text
product-design-agent/
└── workspace/product/
    ├── ds/
    │   └── components.md                   # дописаны строки новых компонентов с Node ID
    └── tasks/<TASK-ID>/analysis/
        └── grow-ui-kit-draft.md            # черновик md-описаний (фаза 2)
```

В Figma: секция «UI Kit — extended» рядом с «Foundation» (не внутри), компоненты плиткой.

Ниже `ds/` означает `workspace/product/ds/`. Существующие строки `components.md` не переписываются — только дописываются новые. `foundation.md` и `CONTRACT.md` этот скилл не меняет; если для компонента не хватает токена или TextStyle, сначала он добавляется по правилам контракта, затем прогон продолжается.
Корневые `CLAUDE.md` и `AGENTS.md` не меняются.
