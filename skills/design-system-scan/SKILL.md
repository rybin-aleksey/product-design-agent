# Индексирование существующей дизайн-системы (ds_scan)

## Назначение

Превратить существующую ДС в Figma в компактный индекс, который агент держит в контексте при сборке экранов:
контекст → `foundation.md` (токены) → `components.md` (каталог с матрицами вариантов и Node ID) → self-check → контракт ДС.
Читаются только Variables и верхний уровень страницы Components, без рекурсии в инстансы. В Figma ничего не меняется.

## Когда использовать

- Запускается из ветки «Подключение существующей дизайн-системы» в [workflows/design-task](../../workflows/design-task/README.md).
- Пользователь просит «проиндексировать / подключить / отсканировать нашу ДС», «работать по корпоративной ДС», «взять ДС из Community».
- ДС уже собрана в Figma, но в `workspace/product/ds/` нет её индекса.
- Повторный прогон: ДС в Figma изменилась и индекс нужно обновить (см. «Обновление индекса» в [methodology.md](methodology.md)).

**Не использовать**, если ДС в Figma нет: тогда нужен скилл [design-system-from-0](../design-system-from-0/SKILL.md).
Если в `workspace/product/ds/CONTRACT.md` указан источник `ds_baseline`, повторный ds_scan запускай только по прямому указанию пользователя.

## Роль

Дизайн-системный архитектор с опытом аудита больших ДС (300+ компонентов). Знает, как работают Figma Variables и `componentPropertyDefinitions`. Читает индексы, а не дерево целиком.

Адаптация роли под источник:

| Источник | Фокус |
|---|---|
| Корпоративная ДС | Аудитор незнакомой ДС: фиксирует как есть, не пытается переделать |
| Дублированная Community-библиотека | Знает базу (Shadcn, Material, Carbon, Gravity UI) и ожидаемые имена компонентов |
| Своя ДС на 200+ компонентов | Дизайн-системщик: помнит часть наизусть, проверяет описания |

## Входные данные

- Контекст продукта из `workspace/product/context/` и папка задачи `workspace/product/tasks/<TASK-ID>/` (для рабочих заметок).
- Ответы на четыре вопроса фазы 1: источник ДС, ссылка **строго на страницу Components**, ссылка на файл с фундаментом (если отдельный), локаль.
- Просмотровый доступ к файлу ДС. Для Community-библиотеки — ссылка на собственную копию (Duplicate to your drafts).

## Фазы

| Фаза | Что делаем | Результат | Гейт |
|---|---|---|---|
| 1. Контекст | Четыре вопроса одним блоком, проверка ссылки | `ds/source.md` | Ссылка ведёт на страницу Components |
| 2. Foundation | Один read-only вызов: Variables и коллекции | `ds/foundation.md` | Файл показан, неясные токены уточнены |
| 3. Components | Один read-only вызов: верхний уровень страницы + self-check | `ds/components.md` | Self-check пройден |
| 4. Показ | Краткая сводка и замечания | Отчёт пользователю | — |
| 5. Контракт | Правила работы с ДС с учётом источника | `ds/CONTRACT.md` | Без фазы 5 прогон не завершён |

Подробности каждой фазы и код чтения — в [methodology.md](methodology.md).
Гейты и проверки — в [checklist.md](checklist.md).
Шаблоны файлов и отчётов — в [output-template.md](output-template.md).

## Жёсткие правила

1. **Никакой рекурсии.** Не заходим в инстансы, не открываем варианты внутри наборов, не идём глубже одного уровня группирующих фреймов и секций.
2. **Только страница Components.** Если ссылка ведёт на корень файла или другую страницу — переспроси, не угадывай. Рекурсивное чтение всей ДС — главная причина падений.
3. **Read-only.** ds_scan ничего не меняет в Figma: ни описаний, ни имён, ни Variables. Описания дополняются в `ds/components.md`, не в Figma.
4. **Только `use_figma`.** Перед первым вызовом загрузи скилл `figma-use`; для Figma MCP сначала `create_session` с `fileKey`. Не использовать read-tools, которые тянут весь файл.
5. **Описания на русском.** Английские `description` переводятся, пустые помечаются в замечаниях.
6. **Матрицы вариантов компактно:** `key: val1 | val2 | val3`, без разворота всех комбинаций.
7. **Node ID обязателен** для каждого компонента.
8. **Self-check обязателен.** Индекс без него уходит в работу с дырами.
9. **Без фазы 5 директива не завершена.** Без контракта индекс остаётся справочником.

## Где сохранять

```text
product-design-agent/
└── workspace/product/ds/
    ├── source.md              # что сканировали и откуда
    ├── foundation.md          # индекс токенов
    ├── components.md          # каталог компонентов с Node ID
    ├── CONTRACT.md            # правила работы с ДС
    └── patterns.md            # опционально, заводится после сканирования
```

Ниже `ds/` означает `workspace/product/ds/`. Все файлы дизайн-системы создаются только там, а не в папке задачи: ДС общая для всех задач продукта. Рабочие заметки прогона кладутся в `workspace/product/tasks/<TASK-ID>/analysis/`.
Корневые `CLAUDE.md` и `AGENTS.md` не меняются: это файлы шаблона агента, а контракт агент находит по правилу в `AGENTS.md`.
Перед созданием файлов проверь, что их ещё нет. Существующий индекс перезаписывай только при повторном сканировании и с согласия пользователя.
