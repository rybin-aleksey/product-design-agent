# Методология: индексирование существующей ДС

Пять фаз. Порядок строгий: каждая следующая начинается только после гейта предыдущей (см. [checklist.md](checklist.md)).
`ds/` означает `workspace/product/ds/`. Все файлы ДС создаются только там.

**Про доступ:** для корпоративной ДС у пользователя должен быть просмотровый доступ к файлу. Для Community-библиотеки сначала Duplicate to your drafts, потом сканирование своей копии.

---

## Фаза 1. Контекст

Задай вопросы одним блоком:

```text
1. Источник ДС: своя / корпоративная / дублированная из Figma Community.
2. Ссылка строго на страницу «Components» в файле ДС (не на корень файла).
3. Если фундамент (Variables) лежит в отдельном файле — ссылка на него. Иначе пометка «фундамент в том же файле».
4. Локаль продукта: ru / en / ru+en. Влияет на проверку шрифтов на кириллицу.
```

- Если локаль уже есть в `workspace/product/context/`, подставь её и попроси подтвердить.
- **Ссылка ведёт на корень файла или другую страницу** — переспроси: «Нужна ссылка именно на страницу Components, иначе MCP захлёбывается на больших ДС». В ссылке на страницу должен быть `node-id`.
- **Источник — Community-библиотека, а Duplicate не сделан** — попроси продублировать к себе и прислать ссылку на копию. Сканирование read-only Community-файла ограничено и теряет половину контекста.
- Сохрани ответы в `ds/source.md` (шаблон в [output-template.md](output-template.md)). Это якорь для всех решений по доводке.

## Фаза 2. Foundation — Variables

### 2.0. Подготовка

- Извлеки `fileKey` из ссылки (`figma.com/design/:fileKey/...`; для веток бери `branchKey`). Если фундамент в отдельном файле, Variables читаются из него.
- Вызови `create_session` с `fileKey`, загрузи скилл `figma-use` и только после этого вызывай `use_figma`.

### 2.1. Чтение Variables

Один read-only вызов `use_figma`. Плоский запрос: на ДС с тысячей токенов отрабатывает за секунды и занимает мало контекста.

```js
const collections = await figma.variables.getLocalVariableCollectionsAsync();
const variables = await figma.variables.getLocalVariablesAsync();
const byId = Object.fromEntries(variables.map(v => [v.id, v]));

const result = collections.map(c => ({
  collection: c.name,
  modes: c.modes.map(m => m.name),
  variables: c.variableIds.map(id => {
    const v = byId[id];
    const value = v.valuesByMode[c.defaultModeId];
    return {
      name: v.name,
      type: v.resolvedType,
      // alias → имя переменной, на которую ссылается; иначе сырое значение
      value: value && value.type === "VARIABLE_ALIAS"
        ? { alias: byId[value.id]?.name ?? value.id }
        : value,
    };
  }),
}));

return result;
```

Если Variables в файле нет (старая ДС на Styles), прочитай `getLocalPaintStylesAsync()` и `getLocalTextStylesAsync()` тем же плоским способом и пометь это в замечаниях.

### 2.2. Сборка `ds/foundation.md`

Структура — по тем же двум-трём слоям, что и в `ds_baseline` (шаблон в [output-template.md](output-template.md)):

- **Слой 1 — примитивы:** палитра, типографика, радиусы, отступы.
- **Слой 2 — смысловые:** только если в ДС есть отдельная коллекция с привязками. Отображай привязки как есть: `surface-default → gray-00`.
- **Слой 3 — компонентные:** если коллекция найдена; иначе раздел опускается.

Правила:
- Цвета из RGB 0–1 переводи в hex.
- Если все Variables в одной плоской коллекции (бывает в старых ДС) — пометь это и предложи разделить на слои. Сам в Figma не разделяй.
- Если у коллекции несколько режимов (light/dark, бренды) — перечисли режимы, значения пиши для режима по умолчанию.
- **Кириллица.** При локали `ru` / `ru+en` отдельно пометь, поддерживает ли шрифт ДС русский и нет ли проблем с Щ/Ъ/Ь/Ы. Шрифт без кириллицы — блокер, выносится в замечания. Если проверить не удалось — так и пиши «не проверена».

Покажи файл пользователю. Пометь места, где сканирование не уверено (например, цвет назван `c-1` и непонятно, акцент это или нейтрал), и сразу попроси уточнить.

## Фаза 3. Components — каталог

### 3.1. Обход верхнего уровня

Один read-only вызов `use_figma`. Берём страницу Components по `node-id` из фазы 1 и читаем только её прямых детей.

```js
const page = await figma.getNodeByIdAsync("<node-id страницы Components>");
await page.loadAsync();

const entry = (node, section) => ({
  section,                                   // имя группирующего фрейма/секции или null
  name: node.name,
  type: node.type,                           // COMPONENT_SET | COMPONENT
  description: node.description,
  // матрица вариантов; у одиночного компонента — только его свойства (TEXT, BOOLEAN, INSTANCE_SWAP)
  properties: Object.fromEntries(
    Object.entries(node.componentPropertyDefinitions).map(([key, def]) => [
      key.replace(/#.*$/, ""),
      def.type === "VARIANT" ? def.variantOptions : def.type,
    ])
  ),
  nodeId: node.id,
});

const isComponent = n => n.type === "COMPONENT_SET" || n.type === "COMPONENT";
const catalog = [];

for (const node of page.children) {
  if (isComponent(node)) {
    catalog.push(entry(node, null));
  } else if (node.type === "FRAME" || node.type === "SECTION") {
    // группировщик: ровно один уровень глубже, без захода в инстансы и внутрь компонентов
    for (const child of node.children) {
      if (isComponent(child)) catalog.push(entry(child, node.name));
    }
  }
  // INSTANCE и children компонентов не читаем
}

return { total: catalog.length, catalog };
```

**Ключевое:** обход — на один уровень вглубь при наличии группирующих фреймов или секций, не дальше. Внутрь компонентов и инстансов не заходим. Это основная защита от таймаута.

**Большие ДС (300+ компонентов).** Если на странице Components вообще всё — попроси автора ДС разбить страницу на разделы. Если нельзя — режь сканирование на прогоны по 50–80 компонентов (по срезу `page.children`) и склеивай `components.md`.

### 3.2. Сборка `ds/components.md`

Шаблон в [output-template.md](output-template.md). Каждый компонент — три-четыре строки в фиксированном формате: назначение, варианты, Node ID.

Правила записи:
- **Группировка по разделам:** Действия, Ввод, Контейнеры, Навигация, Фидбэк, Данные, Прочее — по смыслу из имени или `description`. Если у компонента нет описания и имя неоднозначно — в «Прочее» с пометкой в замечаниях. Имена группирующих секций из Figma можно использовать как подсказку.
- **Матрица вариантов** — строкой `key: val1 | val2 | val3`. Не разворачиваем все комбинации.
- **Node ID обязателен.** По нему агент при сборке экранов вставляет инстансы через `use_figma`.
- **Назначение** — одной строкой. Если `description` заполнено — берём его (с переводом на русский). Если пустое — пишем кратко по имени и помечаем в замечаниях.

### 3.3. Self-check

Пройди по `components.md` и сделай честный review:

- **Доля пустых `Назначение`.** Больше 30% — пометь в замечаниях: после сканирования нужна доводка руками.
- **Наборы с пустым `componentPropertyDefinitions`.** Либо одиночные компоненты без вариантов (норма), либо забытая настройка (проблема). Помечаем.
- **Подозрительные имена:** `Component 1`, `Frame 234`, `Untitled` — в замечания, проверка через автора ДС.
- **Старые версии рядом с новыми:** `Button old`, `Button v1`.
- **Дубликаты имён.** Два набора с одним именем — конфликт, агент при сборке выберет первый. Помечаем явно.

## Фаза 5. Контракт ДС

Цель — закрепить правила работы с ДС для всех следующих задач продукта. После этой фазы при командах «собери экран», «добавь форму», «дорисуй карточку» агент опирается на `ds/components.md`, использует только Variables из `ds/foundation.md` и не отступает от правил без явного «здесь без ДС».

### 5.1. `ds/CONTRACT.md`

Создай по шаблону из [output-template.md](output-template.md). Раздел «Что делать, если нужного нет» адаптируй под источник:

- **Своя / дублированная Community** — недостающий компонент или токен добавляется в Figma-файл ДС, затем в индекс, затем используется на экране.
- **Корпоративная** — ДС править нельзя: сначала композиция из существующих, затем локальный паттерн в `ds/patterns.md` и запрос в команду ДС.

Оставь в контракте только вариант, соответствующий источнику из `ds/source.md`.

Корневые `CLAUDE.md` и `AGENTS.md` не меняй: это файлы шаблона агента. `AGENTS.md` уже требует читать `workspace/product/ds/CONTRACT.md`, если он существует, поэтому любая будущая сессия найдёт контракт сама.

### 5.2. Финальный отчёт

По шаблону из [output-template.md](output-template.md).

## Обновление индекса

ДС живёт. Это ручная процедура, не часть основного прогона, но упомяни её в финальном отчёте:

- Своя или дублированная ДС поменялась в Figma → повторный ds_scan, перезапись `ds/foundation.md` и `ds/components.md` (с согласия пользователя).
- Корпоративная ДС → повторный ds_scan периодически (например, раз в спринт), сравнение с предыдущей версией, пометка устаревших записей; локальные паттерны, которые появились в ДС, убираются из `ds/patterns.md`.
- Ручные правки индекса без сверки с Figma помечаются датой и причиной, иначе следующий ds_scan их затрёт.
