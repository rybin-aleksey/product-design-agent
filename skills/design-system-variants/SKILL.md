# Расширение матрицы вариантов и состояний (component_variants)

## Назначение

Дополнить существующий компонент ДС недостающими вариантами, состояниями и размерами:
текущая матрица → бриф → Semantic-токены (апрув) → md-описание матрицы (апрув) → достройка Component Set в Figma → обновление `components.md` и `foundation.md`.
Один компонент — один прогон и один мутирующий вызов отрисовки.

## Режимы

| Режим | Запуск | Когда |
|---|---|---|
| **Single** | `component_variants <ComponentName>` | Точечная доработка компонента, на котором собирается экран; пользователь точно знает, что добавить |
| **Bulk** | `component_variants` без аргумента | Пройти по всему UI-киту перед сборкой экранов; неизвестно, у каких компонентов матрица неполная |

Bulk — серия single-прогонов: агент находит компоненты с неполной матрицей и по каждому спрашивает, расширять ли. Каждое «да» проходит все фазы с апрувами, «нет» — окончательный пропуск.

## Когда использовать

- Запускается из ветки «Расширение вариантов и состояний» в [workflows/design-task](../../workflows/design-task/README.md).
- Пользователь просит «добавить hover / disabled / focus / loading», «добавить размеры», «добавить ghost-вариант», «доделать состояния компонентов».
- Компонент уже есть в `ds/components.md` и в Figma.

**Не использовать:**
- Если компонента в каталоге нет — это новый компонент, нужен [design-system-grow](../design-system-grow/SKILL.md).
- Если ДС нет — сначала [design-system-from-0](../design-system-from-0/SKILL.md) или [design-system-scan](../design-system-scan/SKILL.md).
- Если источник ДС — **корпоративная**: её файл не правится, недостающие состояния — запрос в команду ДС и пометка в `ds/patterns.md` по контракту.

## Роль

Дизайн-системный архитектор с опытом наращивания матрицы вариантов в существующей ДС. Знает, что write-tools плывут на больших матрицах, поэтому идёт по одному компоненту за прогон. Новые Semantic-токены добавляет только через alias к Primitive.

Адаптация роли под продукт (по `ds/brand-brief.md` или `workspace/product/context/`):

| Продукт | Фокус |
|---|---|
| B2C веб | Состояния action-элементов (Button, Link), focus-кольца на полях ввода |
| B2B SaaS | Состояния в сложных формах, таблицах, dropdown; широкий набор размеров под плотность |
| Мобильное приложение | Тач-состояния (pressed вместо hover), accessibility focus |
| Лендинг | Размеры заголовков и кнопок под breakpoints, минимум состояний (default + hover) |

## Входные данные

- `ds/CONTRACT.md`, `ds/foundation.md`, `ds/components.md` (читаются целиком по правилу `AGENTS.md`), при наличии `ds/source.md` и `ds/brand-brief.md`.
- Имя компонента (single) или ничего (bulk).
- Папка задачи `workspace/product/tasks/<TASK-ID>/` — для черновиков описаний.
- Ссылка на Figma-файл ДС, если её нет в `CONTRACT.md` / `source.md`.

## Фазы

| Фаза | Что делаем | Результат | Гейт |
|---|---|---|---|
| 1. Read | Строка в `components.md` + read-only чтение компонента в Figma | Текущая матрица | Расхождения md ↔ Figma решены пользователем |
| 2. Brief | Три вопроса: варианты, состояния, размеры | Список добавлений | Ответы конкретные, без «по умолчанию» |
| 3. md | Новая матрица и её размер, Semantic-токены, описание ячеек | `analysis/component-variants-<name>.md` | **Апрув токенов и апрув описания** |
| 4. Canvas | Semantic Variables (если нужны), промоут в Set, достройка ячеек, проверка | Расширенный Component Set | Проверка по факту пройдена |
| 5. Каталог | Обновить строку в `components.md`, дописать токены в `foundation.md` | Актуальный индекс | — |
| 6. Отчёт | Single или bulk-отчёт | Отчёт пользователю | — |

Подробности фаз, код и правила отрисовки — в [methodology.md](methodology.md).
Гейты и проверки — в [checklist.md](checklist.md).
Шаблоны описаний и отчётов — в [output-template.md](output-template.md).

## Жёсткие правила

1. **Никаких мутирующих MCP-вызовов до апрува токенов и md-описания.** Read-only чтение компонента в фазе 1 разрешено.
2. **Один компонент — один мутирующий вызов отрисовки.** Bulk — серия single-прогонов, а не пакет.
3. **Матрица 25+ ячеек дробится** на два прогона с промежуточным апрувом (если пользователь не настоял на одном).
4. **Дефолтов нет.** Какие варианты и состояния добавлять — продуктовое решение пользователя.
5. **Имена ячеек — `Property=value` через запятую** (`Type=primary, State=hover, Size=md`). Существующие имена осей сохраняются; переименование оси — только с согласия пользователя.
6. **Fills, strokes — только через Semantic Variables**; padding, gap, радиусы — через Primitive `space-*` / `radius-*`; типографика — через существующие TextStyles. Прибитые hex и числа запрещены.
7. **Новые Semantic — только alias к Primitive.** Нет подходящего Primitive — сначала Primitive (с апрувом), потом Semantic.
8. **Существующие ячейки не пересоздаются**: на них уже стоят инстансы на экранах.
9. **Auto Layout в каждой ячейке.**
10. **Loading без анимации**, только плейсхолдер под спиннер.
11. **Никакого `throw` в конце мутирующего вызова**: он откатывает всю транзакцию.
12. **Bulk не возвращается к пропущенным компонентам** без запроса пользователя.

## Где сохранять

```text
product-design-agent/
└── workspace/product/
    ├── ds/
    │   ├── components.md                         # обновлена матрица у затронутых компонентов
    │   └── foundation.md                         # добавлены Semantic-токены (если потребовались)
    └── tasks/<TASK-ID>/analysis/
        └── component-variants-<name>.md          # черновик описания по каждому компоненту
```

Ниже `ds/` означает `workspace/product/ds/`. В `components.md` меняется только строка затронутого компонента, в `foundation.md` токены только дописываются, существующие не правятся.
Корневые `CLAUDE.md` и `AGENTS.md` не меняются.
