# Сборка финальных экранов (final_screens)

## Назначение

Собрать финальный экран продукта в Figma: каркас wireframe заменяется инстансами компонентов из UI-кита, всё привязано к ДС, edge cases заложены сразу.
ресурсы (иконки, тени) → wireframe и каталог → анализ достаточности → повторяющиеся блоки → composition map (апрув) → вынос новых компонентов → pre-canvas check → сборка → запись в каталог.

## Режимы

| Режим | Запуск | Когда |
|---|---|---|
| **Single** | `final_screens <ScreenName>` | Один экран, полный контроль над composition map, нестандартная композиция |
| **Bulk** | `final_screens` без аргумента | Wireframes готовы, ДС готова, экраны типовые (Dashboard / List / Settings / Profile / Form) |

Bulk — серия single-прогонов: агент идёт по фреймам секции «Wireframes», пропускает уже собранные в «Screens» и по каждому спрашивает, собирать ли. Каждое «да» проходит все фазы с апрувами.

## Когда использовать

- Запускается из ветки «Сборка финальных экранов» в [workflows/design-task](../../workflows/design-task/README.md).
- Пользователь просит «собрать экран», «сделать финальный макет по wireframe», «перевести wireframes в UI».
- Есть `ds/CONTRACT.md` и непустой `ds/components.md`, а в Figma — wireframe экрана.

**Не использовать:**
- Нет ДС — сначала [design-system-from-0](../design-system-from-0/SKILL.md) или [design-system-scan](../design-system-scan/SKILL.md).
- Нет wireframe — сначала wireframe (отдельная задача; в шаблоне для неё пока нет скилла). Собирать экран без wireframe — только по прямому указанию пользователя, тогда структуру задаёт composition map.

## Роль

Дизайнер-сборщик с практикой сборки экранов из wireframe и готовой ДС. Отличает instance от detached-копии и всегда сохраняет связь с Component Set. Закладывает edge cases сразу. Сначала фиксирует структуру в md, и только после апрува пишет на канвас.

Адаптация роли под продукт (по `workspace/product/context/` и `ds/brand-brief.md`):

| Продукт | Фокус |
|---|---|
| B2C веб (магазин, медиа, лендинг) | Hero, секционная вёрстка, состояния карточки товара, корзина, чекаут |
| B2B SaaS (dashboard, CRM, админка) | Плотность данных, таблицы, фильтры, sidebar, empty states, скелетоны, роли |
| Мобильное приложение | Нижняя навигация, sheet / drawer, скролл-списки, офлайн |
| Внутренняя админка | Меньше лоска, больше edge cases: длинные значения, многоколоночность, сортировки, bulk-actions |

## Принципы

Применяются в каждом прогоне, а не как полировка после фидбэка. Подробно — в [methodology.md](methodology.md#принципы).

1. **Sizing — это смысл.** FILL / HUG / FIXED по таблице; `FIXED × FIXED` для секций запрещён.
2. **Компоненты — только instance** от Component Set по Node ID, нужный вариант через `setProperties`.
3. **Цвета, отступы, радиусы — через Variables, типографика — через TextStyles ДС.**
4. **Иконки — реальные SVG из выбранной библиотеки** с первой итерации, а не серые квадраты.
5. **Тени из Foundation (EffectStyles) — база**, применяются сразу.
6. **Overview / dashboard не пустой:** ориентир — 60% площади занято осмысленным контентом.
7. **Структурированная мета:** поля сущности — отдельными элементами (иконка + текст, chips, badges), а не строкой через `·`; справочные ссылки — кликабельные.
8. **3+ копии блока — компонент в UI-ките**, вынесенный в этом же прогоне.

## Входные данные

- `ds/CONTRACT.md`, `ds/foundation.md`, `ds/components.md` (целиком, по правилу `AGENTS.md`), при наличии `ds/source.md`, `ds/brand-brief.md`, `ds/icons.md`.
- Контекст продукта из `workspace/product/context/` — для реалистичного демо-контента и выбора секций.
- Папка задачи `workspace/product/tasks/<TASK-ID>/`.
- Figma-файл, где лежат секции «Wireframes» и «Foundation».

## Фазы

| Фаза | Что делаем | Результат | Гейт |
|---|---|---|---|
| 0. Ресурсы | Библиотека иконок, наличие теней | Иконки и тени зафиксированы | Ответ пользователя |
| 1. Read | Wireframe read-only, каталог, сверка покрытия, анализ достаточности, повторяющиеся блоки | Решения по каждому пункту | **Решения пользователя по всем пунктам** |
| 2. Composition map | md-карта экрана | `artifacts/design/screens/<name>.md` | **Апрув** |
| 2.5. Вынос в UI-кит | Мини-цикл grow для блоков 3+ копий, новые Semantic через alias | Новые компоненты и токены в Figma и md | **Апрув брифов и токенов**, аудит пройден |
| 3. Pre-canvas check | Десять проверок перед записью | — | Все пункты закрыты |
| 4. Canvas | Секция «Screens», фрейм `Screen/<Name>`, проверка | Экран в Figma | Проверка по факту пройдена |
| 5. Каталог | `used in` в `components.md`, индекс экранов | Обновлённые md | — |
| 6. Отчёт | Single или bulk | Отчёт пользователю | — |

Подробности фаз и код — в [methodology.md](methodology.md).
Гейты — в [checklist.md](checklist.md).
Шаблоны composition map и отчётов — в [output-template.md](output-template.md).

## Жёсткие правила

1. **Никаких мутирующих MCP-вызовов до апрува composition map** (и брифов фазы 2.5). Read-only чтение wireframe разрешено.
2. **Wireframe — исходник, а не финальный layout.** Анализ достаточности (фаза 1.4) обязателен, но каждое дополнение — только с согласия пользователя.
3. **Компоненты ДС — только instance.** Найден `FRAME` вместо `INSTANCE` — пересборка блока.
4. **Нет компонента под секцию — решение пользователя:** вынести в UI-кит, взять ближайший или оставить плейсхолдер. Не собирать «похожий» на месте.
5. **Прибитые hex и числа запрещены** на уровне экрана и секций; на инстансах — без override с прибитым цветом.
6. **Новые Semantic — только alias к Primitive.**
7. **Один экран — один мутирующий вызов** (большой экран — несколько вызовов по секциям в тот же фрейм). Без `throw` в конце мутирующего вызова.
8. **Edge cases — в том же фрейме**, `visible: false`.
9. **Главный фрейм — `Screen/<Name>`**, секции — простыми латинскими именами.
10. **Bulk не пересобирает собранные экраны** без явного запроса и не возвращается к пропущенным.
11. **Демо-контент не выдаёт себя за факты.** Цифры, имена, статусы на макете — иллюстративные, берутся из контекста продукта, если он есть; в composition map помечаются как демо.
12. **Корпоративная ДС:** фаза 2.5 не выносит компоненты в файл ДС — повторяющиеся блоки оформляются локальным паттерном в `ds/patterns.md` по контракту.

## Где сохранять

```text
product-design-agent/
└── workspace/product/
    ├── ds/
    │   ├── components.md                     # used in + новые компоненты из фазы 2.5
    │   ├── foundation.md                     # новые Semantic из фазы 2.5 (если были)
    │   └── CONTRACT.md                       # строка «Icon library» (фаза 0, с согласия)
    └── tasks/<TASK-ID>/
        ├── analysis/
        │   └── final-screens-extract-<name>.md   # брифы выносимых компонентов (фаза 2.5)
        └── artifacts/design/screens/
            ├── _index.md                     # экраны, собранные в задаче
            └── <name>.md                     # composition map экрана
```

`ds/` означает `workspace/product/ds/`. Composition map — материал задачи, поэтому лежит в её `artifacts/`, а не в `ds/`. В `components.md` строка `used in` ссылается на `<TASK-ID>/screens/<name>`.
Существующие записи и файлы дописываются, а не перезаписываются. Корневые `CLAUDE.md` и `AGENTS.md` не меняются.
