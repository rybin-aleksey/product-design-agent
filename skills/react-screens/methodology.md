# Методология: сборка экрана из базы

`code/` — `workspace/product/code/`, `ds/` — `workspace/product/ds/`. Команды выполняются в `code/`.
Self-check — в [checklist.md](checklist.md).

---

## Фаза 0. Контекст и каркас

1. Прочитай `ds/CONTRACT.md`, `ds/components.md`, `code/src/components/index.ts` — что есть в базе и под какими именами.
2. Посмотри, как устроена база: способ стилей (CSS Modules / CSS-переменные / другое), точка входа, есть ли роутер (`react-router-dom` или аналог в `package.json`), есть ли `src/screens/`.
3. Каркас экранов — «среда для экранов»:
   - **роутер** — используй существующий. Нет — предложи: `react-router-dom` (одна зависимость) или минимальный hash-роутер без зависимостей (`window.location.hash` + `hashchange`). Ставить зависимость — только с согласия.
   - **реестр** `src/screens/registry.ts` — нет, заведи пустой;
   - **индекс** `src/screens/ScreensIndex.tsx` на «/» — нет, собери (см. фазу 5).
   Роуты в роутере генерируются из реестра, а не перечисляются руками.
4. Если в реестре уже есть этот экран — это повторный запуск (фаза 7).

## Фаза 1. Ссылка на фрейм

Один запрос:

```text
Пришли ссылку на сам фрейм экрана в Figma: правый клик по фрейму → Copy link to selection. Ссылка на корень файла не подойдёт.
```

- В ссылке должен быть `node-id`. Нет — переспроси: по корню файла MCP отдаёт только первую страницу, экран не прочитается.
- Разбери `fileKey` и `nodeId` (`-` → `:`), для веток — `branchKey`.
- Имя экрана: из имени фрейма (`Screen/Dashboard` → `Dashboard`, папка `dashboard`, роут `/dashboard`). Неясно — уточни.

## Фаза 2. Чтение дизайна

Перед вызовами — `create_session` с `fileKey`; перед `get_design_context` — загрузи скилл `figma-design-to-code` (обязательное условие Figma MCP).

1. `get_metadata` по `nodeId` — карта фрейма: секции, вложенность, типы, размеры. Без тяжёлого контента.
2. `get_design_context` **по секциям** (header, body, крупные блоки), а не по всему фрейму: большой фрейм переполняет контекст. Забираешь раскладку, имена слоёв, инстансы компонентов и их варианты, токены.
   Результат `get_design_context` — референс, а не готовый код: адаптируй под базу и токены проекта.
3. `get_screenshot` по фрейму — визуальный референс для сверки.
4. Если есть composition map экрана — сверь с ним: компоненты, варианты, локальные блоки, edge cases (скрытые состояния в коде не собираются — это данные и логика; упомяни их в заметке).

## Фаза 3. Декомпозиция

Пройди структуру сверху вниз и составь карту блоков:

| Блок макета | Решение |
|---|---|
| Инстанс компонента ДС, который есть в базе (`Button`, `Card`, `Navbar`, `Badge`, `Table`) | `<Component>` из базы, варианты → пропсы |
| Компонент ДС, которого нет в базе (например, `ServerCard`, вынесенный в final-screens) | Спросить: добавить в базу отдельной задачей (рекомендуется — он уже часть ДС) или временно собрать локальным блоком |
| Доменная композиция без компонента ДС | Локальный блок `parts/<Block>.tsx` из базы и токенов; пометка «кандидат на вынос» |
| Фрейм-обёртка с Auto Layout | Разметка экрана (`div` / семантический тег) с flex / grid |
| Изображение, логотип | Плейсхолдер на токенах |
| Иконка | Библиотека из `ds/CONTRACT.md`, если она уже есть в зависимостях базы (например, `lucide-react`); иначе плейсхолдер |

Правила:
- Сопоставление — по имени инстанса и структуре, варианты — по `variantProperties` / свойствам из контекста.
- Нет точного совпадения — локальный блок, а не «натянутый» чужой компонент.
- Блок встречается и на другом собранном экране (по реестру и заметкам) — предложи вынести в базу.
- Детачнутые элементы в макете (фреймы, похожие на компонент) — используй компонент базы и отметь в заметке, что в Figma он детачнут (повод для screens-audit).

## Фаза 4. Сборка страницы

### Раскладка

| Figma | CSS |
|---|---|
| Auto Layout vertical / horizontal | `display: flex; flex-direction: column / row` |
| `itemSpacing` | `gap: var(--space-*)` |
| `padding*` | `padding: var(--space-*)` |
| Primary axis align: start / center / end / space-between | `justify-content` |
| Counter axis align | `align-items` |
| FILL (по главной оси) | `flex: 1 1 0; min-width: 0` |
| FILL (по поперечной оси) | `align-self: stretch` |
| HUG | без размера (по контенту), `flex: 0 0 auto` |
| FIXED | `width` / `height` — токен, если есть; иначе значение из макета и пометка в заметке |
| `layoutWrap = WRAP` | `flex-wrap: wrap` (+ `row-gap` из `counterAxisSpacing`) |
| Сетка карточек равной ширины | `display: grid; grid-template-columns: repeat(auto-fill, minmax(<min>, 1fr))` |
| Констрейнты Left & Right / Scale | растяжение по ширине контейнера |
| Корневой экран 1440 | `min-height: 100vh`, ширина 100%, контент — `max-width` по макету и центрирование |

Цель — экран держится при смене ширины и при более длинном контенте: `min-width: 0` у flex-детей, перенос длинных строк (`overflow-wrap: anywhere` для значений), без фиксированных высот у контейнеров с текстом.

### Стили

- Только семантические токены: `var(--surface-*)`, `var(--text-*)`, `var(--border-*)`, `var(--space-*)`, `var(--radius-*)`, тени — токенами из базы.
- Типографика — классами / компонентами текста базы, если они есть; иначе токенами размера, веса и межстрочного.
- Стили экрана — в том же формате, что принят в базе (например, `<Name>.module.css`).

### Контент

- Статикой, **ровно как в макете**: те же тексты и значения. Повторяющиеся элементы — повтор JSX или локальный массив литералов для `map` прямо в файле экрана (это разметка, не слой данных).
- Ничего не выдумывать сверх макета; не создавать моков, сервисов, хуков, контекстов, `useState` / `useEffect`.
- Ссылки и кнопки — без обработчиков (`href="#"` не нужен; кнопки — как есть, без `onClick`).

## Фаза 5. Подключение

1. Страница — `src/screens/<name>/<Name>.tsx` (default export или именованный — как принято в базе).
2. Запись в `src/screens/registry.ts`: `id`, `name`, `description` (одна строка: ключевые блоки), `route`, `component` (ленивая загрузка, если в проекте так принято). Перед добавлением — проверка на дубль `id` и `route`.
3. Индекс «/» строится из реестра — новый экран появляется плиткой сам.
4. Заметка `src/screens/<name>/<name>.md` по шаблону из [output-template.md](output-template.md).

### Навигационная страница-индекс (обязательна)

Одна страница на «/», собранная на компонентах базы и токенах (выглядит как продукт, а не служебная заглушка):
- заголовок — `<Продукт> — экраны` (имя продукта из контекста);
- подзаголовок: «Статичные экраны, собранные из дизайн-системы. Логика и данные — отдельный шаг.»;
- сетка плиток из реестра: название, описание, роут; вся плитка — ссылка на экран (через роутер), с видимым focus;
- внизу — ссылка на каталог Storybook, если он есть в проекте (скрипт `storybook` в `package.json`); нет — блок не выводится;
- пустой реестр — понятное пустое состояние («Экранов пока нет»).

На каждом экране — небольшая ссылка «← Все экраны» на «/» (вне макета экрана, например фиксированный уголок), чтобы между экранами было удобно ходить. Это навигация среды, а не логика экрана.

## Фаза 6. Запуск и проверка

1. `npm run dev` — **в фоне**; дождись адреса. Проверка типов / сборки (`npm run build` или `tsc --noEmit`, если есть).
2. Открой «/» и роут экрана (встроенный браузер, если доступен). Сверь со скриншотом из Figma: компоненты, раскладка, отступы, сетка.
3. Проверка устойчивости: ширина окна от мобильной до широкой; контент длиннее макетного (длинный заголовок, больше элементов в списке) — временно в devtools или во временной правке, которую потом откатить. Раскладка держится, ничего не вылезает.
4. Консоль без ошибок; остальные экраны из реестра открываются.
5. Покажи пользователю индекс и роут. Расхождения он называет словами — правки вносит агент.

## Фаза 7. Повторный запуск

- **Новый экран** — фазы 1–6, добавить в реестр; остальные экраны не трогать.
- **Тот же экран** (по `id` / роуту в реестре или по ссылке на тот же фрейм) — пересобрать страницу, локальные блоки и заметку; роут и запись в реестре не дублировать, обновить `description`, если изменилось. В отчёте — что изменилось.
- Локальный блок появился на втором экране — предложить вынос в базу (отдельная задача).
