# Оживление экранов: навигация, данные, поведение (wire)

## Назначение

Превратить статичные экраны из [react-screens](../react-screens/SKILL.md) в кликабельный продукт на моке, по которому можно ходить и тестировать:
контекст и скоуп → навигация → слой мок-данных → формы и поведение → состояния и edge cases → (опц.) анимации → прокликивание.
Логику формулирует пользователь, обработчики пишет агент; в код пользователь не лезет.

## Граница: что НЕ делаем

- **Не подключаем бэкенд, API, базу данных, авторизацию.** Только мок-слой в коде.
- **Не деплоим и не ставим метрики / трекинг** — отдельные задачи.
- **Не пересобираем экраны и не переписываем базу компонентов.** Берём готовое и оживляем; правка базы (например, недостающий проп состояния) — только с согласия и на токенах.

## Когда использовать

- Запускается из ветки «Оживление экранов» в [workflows/design-task](../../workflows/design-task/README.md) **только по явной команде пользователя** (`wire`, «оживи экраны», «сделай кликабельным»). Задача с кодом — прямой запрос обязателен по `AGENTS.md`.
- Статичные экраны собраны и зарегистрированы в `src/screens/registry.ts`, есть роутер и индекс «/».
- Переиспользуемый: оживить первый экран, потом другой; добавить поведение; позже — анимации. Каждый запуск дополняет.

**Не использовать**, если статичных экранов нет — сначала [react-screens](../react-screens/SKILL.md).

## Роль

Фронтенд-разработчик прототипов: делает из макетов проходимый продукт на моке, не забывает про пустые, ошибочные и граничные состояния, держит всё на компонентах базы и токенах. Переводит продуктовую логику пользователя в обработчики и задаёт уточняющие вопросы там, где макет молчит.

## Входные данные

- `ds/CONTRACT.md`, `ds/components.md` — правила, токены состояний, компоненты под состояния (Toast, Badge, Banner, пустые состояния).
- `code/src/screens/registry.ts`, экраны и их заметки `src/screens/<name>/<name>.md`.
- Edge cases из дизайна: разделы «Edge cases» в composition maps (`workspace/product/tasks/*/artifacts/design/screens/*.md`), решения последнего отчёта [screens-audit](../screens-audit/SKILL.md).
- Контекст продукта — для реалистичных мок-данных и доменных edge cases.

## Фазы

| Фаза | Что делаем | Результат | Гейт |
|---|---|---|---|
| 0. Контекст и скоуп | Реестр, экраны, заметки, edge cases из дизайна; выбор экранов / сценария | Скоуп запуска | Скоуп подтверждён |
| 1. Навигация | Переходы по меню / кнопкам / ссылкам, «назад», активный пункт, 404 | Проходимые экраны | — |
| 2. Мок-данные | Единый слой `src/data/`, экраны читают из него | Данные вместо статики | Экраны выглядят как до перевода |

| 6. Проверка | Прокликать сценарий, искать дыры, переключатель сценариев | Отчёт | Self-check пройден |
| 7. Повтор | Наращивание без поломок | — | — |

## Жёсткие правила

1. **Только мок.** Никаких реальных запросов, ключей, внешних API.
2. **Один слой данных** в `src/data/`; экраны не держат собственные копии данных.
3. **Перевод статики в данные обязателен:** начальные мок-данные = контент из макета, поэтому экран после перевода выглядит так же.
4. **Edge cases — стандарт, а не опция:** загрузка, успех, ошибка, пусто, невалидный ввод, границы, доменные края.
5. **Логику задаёт пользователь.** Очевидное из макета агент делает сам; продуктовую логику, которой нет в макете, — спрашивает и не выдумывает.
6. **Только компоненты базы и семантические токены** (`CONTRACT`), включая новые состояния.
7. **Новые зависимости** (стейт-менеджер, формы, анимации, роутер) — только с согласия; по умолчанию — средства React и уже установленного.
8. **Повторный запуск наращивает:** мок-слой и навигация переиспользуются, существующее не переписывается.
9. **Доступность:** фокус в модалках, `aria-live` для тостов и ошибок, связь ошибки с полем, `prefers-reduced-motion` для анимаций.
10. **Ничего не коммитим** без прямого указания.

## Где сохранять

```text
workspace/product/code/src/
├── data/
│   ├── types.ts              # типы сущностей
│   ├── fixtures.ts           # начальные мок-данные (контент из макета + реалистичное расширение)
│   ├── store.tsx             # единое хранилище и действия (Context + reducer или принятое в базе)
│   ├── api.ts                # мок-«запросы» с задержкой и управляемой ошибкой
│   └── scenarios.ts          # сценарии для проверки: empty / error / zero-balance / …
└── screens/<name>/
    ├── <Name>.tsx            # оживлённый экран
    └── <name>.md             # заметка: раздел «Поведение» дописан
```

Если в базе уже принят другой способ (стейт-библиотека, структура папок) — следуй ему. Корневые `CLAUDE.md` и `AGENTS.md` не меняются.
