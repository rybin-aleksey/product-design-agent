## Фаза 1. Навигация

- Пункты меню, кнопки и ссылки ведут на экраны реестра; маршруты берутся из реестра, а не пишутся строками в каждом экране (хелпер `routeOf('dashboard')`).
- «Назад» — история браузера; у вложенных экранов — явная ссылка назад, если она есть в макете.
- Активный пункт меню подсвечивается по текущему роуту (через проп активного состояния компонента навигации из базы).
- Неизвестный роут — экран 404 на компонентах базы со ссылкой на индекс.
- Экран, на который в макете ведёт кнопка, но которого нет в реестре, — не придумывать: сообщить пользователю (собрать через react-screens или оставить действие с Toast «Экран в разработке» — по его решению).
- Индекс «/» и ссылка «← Все экраны» из react-screens остаются как навигация среды.

## Фаза 2. Слой мок-данных

1. **Модель.** По статичному контенту экранов выдели сущности и поля (`Server { id, name, status, ip, region, specs, uptime }`, `Balance`, `Operation`) → `src/data/types.ts`.
2. **Начальные данные** — `src/data/fixtures.ts`: сначала ровно то, что было в макете (экран после перевода выглядит так же), затем при необходимости реалистичное расширение (больше элементов, разные статусы, длинные значения) — в стиле контекста продукта, без выдуманных фактов о бизнесе. Всё помечено как демо.
3. **Хранилище** — `src/data/store.tsx`: один источник правды и действия над ним. По умолчанию — React Context + `useReducer` (без новых зависимостей). Действия — именованные (`createServer`, `topUpBalance`, `deleteServer`), а не прямые мутации из экранов.
4. **Мок-«API»** — `src/data/api.ts`: асинхронные функции с небольшой задержкой (300–800 мс), чтобы были видны состояния загрузки, и управляемой ошибкой (по сценарию), чтобы было видно состояние ошибки. Никаких сетевых запросов.
5. **Перевод экранов:** литералы и локальные массивы из react-screens заменяются чтением из хранилища (хуки `useServers()`, `useBalance()`). Разметка экрана не переписывается.
6. **Сохранение между перезагрузками** — по умолчанию нет (каждый запуск — чистое демо). Нужно — по запросу пользователя через `localStorage` с try/catch и кнопкой «Сбросить демо-данные».

## Фаза 3. Формы и поведение

1. **Формы:** контролируемые поля, сбор значений, отправка → действие хранилища через мок-API → результат на экране (запись в списке, обновлённое значение, переход, Toast).
2. **Валидация** — на отправку и при уходе с поля после первой ошибки:
   - обязательные поля; форматы (email, IP, телефон — по полю); границы (пустое, слишком длинное, ноль, минус, больше лимита);
   - ошибка — состояние поля из базы (`state="error"` + текст), связанный с полем (`aria-describedby`), фокус на первое поле с ошибкой;
   - во время отправки кнопка в состоянии loading, повторная отправка заблокирована.
   Библиотеку форм и схем не подключать без согласия.
3. **Логика:**
   - **очевидное из макета** — делает агент сам: submit формы, переход по кнопке, создание → появление в списке, закрытие модалки по «Отмена» / Esc;
   - **продуктовая логика, которой нет в макете** — список вопросов пользователю одним блоком (шаблон в [output-template.md](output-template.md)): что происходит по действию, какие ограничения, какие тексты. Без ответа — не выдумывать; можно временно оставить действие с Toast «Логика не определена» и пометкой в заметке.
4. Ответы пользователя записываются в заметку экрана, раздел «Поведение» — это спецификация логики для разработки.

## Фаза 4. Состояния и edge cases

### Стандартный набор (обязателен для каждого действия и списка в скоупе)

| Состояние | Как показывается |
|---|---|
| Загрузка | Skeleton / Spinner из базы на месте контента; loading у кнопки действия |
| Успех | Toast success (`aria-live="polite"`), обновлённые данные |
| Ошибка | Toast error или inline-ошибка с действием «Повторить»; данные не теряются |
| Пусто | Empty state: текст + основное действие (из composition map, если есть) |

### Edge cases

- Невалидный ввод и граничные значения: ноль, минус, слишком много / длинно, дубликат имени.
- Доменные края по продукту (например, нулевой / низкий баланс → баннер и блокировка платного действия; лимит сущностей; удаление последнего элемента → пусто).
- «Ничего не найдено» для поиска и фильтров, со сбросом фильтра.
- Переполнение: длинные имена, много элементов — раскладка держится.
- Деструктивные действия — подтверждение (Modal) перед выполнением.

Сначала — edge cases из дизайна (фаза 0). Затем **предложи дополнительные по продукту**, которых нет в макете, одним списком — пользователь выбирает, какие добавить.

Все состояния — из компонентов базы и семантических токенов (`--surface-error-*`, `--text-error`, `--border-error` и т.п.). Нет нужного токена — не прибивать значение, а предложить добавить в Foundation отдельной задачей.

### Переключатель сценариев (для проверки)

`src/data/scenarios.ts` + параметр `?scenario=empty|error|slow|zero-balance` (или dev-панель на индексе «/»): подменяет начальные данные и поведение мок-API, чтобы любое состояние можно было показать без ручных манипуляций. Это инструмент среды, не часть продукта; в заметках экранов перечислены доступные сценарии.

## Фаза 5. Анимации (по желанию)

Предложи; делай только при согласии — сейчас или отдельным повторным запуском.
- Переходы между экранами, появление / исчезновение элементов (добавление в список, тосты, модалки), микро-взаимодействия.
- 150–250 мс, ease; длительность и easing — через motion-токены, если они есть (нет — предложить завести).
- CSS-переходы и `@keyframes` по умолчанию; библиотека анимаций — только с согласия.
- `prefers-reduced-motion: reduce` — анимации отключаются.
- Поведение не зависит от анимации (данные обновляются сразу, анимация — поверх).

## Фаза 6. Прокликать и проверить

1. `npm run dev` в фоне; сборка / типы (`npm run build` или `tsc --noEmit`).
2. Пройди оживлённый сценарий целиком, как пользователь (во встроенном браузере, если доступен): основной путь, затем каждый сценарий из переключателя.
3. Ищи дыры: тупик без выхода; действие без реакции; непредусмотренное состояние; потеря введённых данных при ошибке; двойная отправка; кривой переход; ошибки в консоли.
4. Клавиатура: Tab по форме, Enter отправляет, Esc закрывает модалку, фокус возвращается.
5. Покажи пользователю, что подключено и как включить сценарии. Расхождения он называет словами — правки вносит агент.

## Фаза 7. Повторный запуск = наращивание

- **Ещё экран / сценарий** — фазы 1–4 для него; мок-слой и навигация переиспользуются, новые сущности — дописываются в `types.ts` / `fixtures.ts`.
- **Ещё поведение** — конкретная логика по запросу, запись в «Поведение».
- **Анимации** — фаза 5 поверх.
- Существующие обработчики и данные не переписываются; дублирующих хранилищ и хелперов не появляется. В отчёте — что добавлено.
