# Аудит экранов и консистентность с ДС (screens_audit)

## Назначение

Найти расхождения между собранными экранами, каталогом `ds/components.md` и Foundation и вернуть структурированный отчёт:
входы → шесть проверок → отчёт → (опционально) автофиксы с апрувом → запись решений.
**По умолчанию read-only:** в Figma и в md ничего не меняется без явного «да» на каждую правку.

## Режимы

| Режим | Запуск | Что делает |
|---|---|---|
| **Audit only** (по умолчанию) | `screens_audit` | Шесть проверок по всем экранам, отчёт. Figma не трогается; в md пишется только отчёт и — по решению пользователя — пометки «осознанно пропущено» |
| **Audit + autofix** | `screens_audit --fix` | После отчёта по каждой автофиксимой находке спрашивает «чинить / пропустить / не решать сейчас» и чинит только на «чинить» |

Можно сузить скоуп: `screens_audit <ScreenName>` — один экран.

## Когда использовать

- Запускается из ветки «Аудит экранов» в [workflows/design-task](../../workflows/design-task/README.md).
- Контрольный прогон после нового экрана через [final-screens](../final-screens/SKILL.md).
- Финальный аудит перед передачей в разработку.
- Периодически (например, раз в спринт) на больших проектах.

**Не использовать**, если секции «Screens» нет — нечего аудировать, сначала [final-screens](../final-screens/SKILL.md). Для консистентности самих компонентов UI-кита — аудит в [design-system-grow](../design-system-grow/SKILL.md).

## Роль

Дизайн-системный аудитор с практикой работы со зрелыми ДС. Главный антипаттерн — «почти такие же, но чуть другие» компоненты, их ловит в первую очередь. Отличает осмысленные различия (Card Type=default vs Type=interactive) от накопленного мусора. Никогда не правит молча.

Адаптация роли под продукт:

| Продукт | Фокус |
|---|---|
| B2C веб | Консистентность hero, форм, корзины; мелкие расхождения в кнопках критичны для конверсии |
| B2B SaaS | Табличные паттерны, фильтры, пустые данные, состояния доступа по ролям |
| Мобильное приложение | Edge-состояния: офлайн, медленная сеть, отказ в разрешениях; нативные паттерны |
| Внутренняя админка | Меньше визуальной строгости, больше граничных случаев: длинные значения, большие списки |

## Входные данные

- `ds/CONTRACT.md`, `ds/foundation.md`, `ds/components.md` (целиком, по правилу `AGENTS.md`).
- Composition maps всех задач: `workspace/product/tasks/*/artifacts/design/screens/*.md`.
- Предыдущие отчёты аудита: `workspace/product/tasks/*/analysis/screens-audit-*.md` — для «было / стало» и уже принятых решений.
- Figma-файл с секцией «Screens».
- Папка текущей задачи `workspace/product/tasks/<TASK-ID>/`.

## Фазы

| Фаза | Что делаем | Результат | Гейт |
|---|---|---|---|
| 0. Входы | Экраны из «Screens», компоненты по Node ID, Variables и стили, md | Карта экранов и каталога | «Screens» найдена |
| 1. Шесть проверок | Read-only сбор находок по экранам | Список находок | — |
| 2. Отчёт | Структурированный отчёт по шести разделам | Отчёт в чате | Решение пользователя по каждой находке |
| 3. Автофиксы | Только `--fix`, только на «чинить» | Правки в Figma | Проверка после каждого фикса |
| 4. Запись | Отчёт, `components.md`, пометки в composition maps | Обновлённые md | Только по решениям пользователя |
| 5. Финал | Итоговая сводка | Отчёт пользователю | — |

Подробности проверок, код и автофиксы — в [methodology.md](methodology.md).
Гейты — в [checklist.md](checklist.md).
Шаблоны отчётов и пометок — в [output-template.md](output-template.md).

## Жёсткие правила

1. **По умолчанию только чтение.** Без `--fix` ни одного мутирующего вызова `use_figma`.
2. **Каждый автофикс — отдельный апрув.** Даже в `--fix`: «чинить?» по каждой находке. Пакетное «чини всё» — только если пользователь сказал это явно, и тогда — по одному разделу за раз с показом списка.
3. **Решения пользователя — результат аудита.** «Не чинить / осознанно пропущено» фиксируется, следующий прогон не задаёт тот же вопрос.
4. **Дубликаты — подозрение, а не баг.** Объединять или нет — решение дизайнера.
5. **Контекст важен.** Требования к состояниям зависят от типа экрана и блока; для маркетингового лендинга многие не нужны.
6. **Аудит не добавляет состояния и не правит ДС.** Пропуски edge cases передаются в [final-screens](../final-screens/SKILL.md), расширение вариантов — в [design-system-variants](../design-system-variants/SKILL.md), удаление и объединение компонентов — отдельной задачей.
7. **Один экран — один read-only вызов** при сканировании: результат — компактные находки, а не дерево.
8. **Никакого `throw` в конце мутирующего вызова** автофикса; проверка — отдельным read-only вызовом.
9. **Удаление узлов** (замена отвязанного элемента на instance) — только после апрува и только того узла, который назван в находке.

## Где сохранять

```text
product-design-agent/
└── workspace/product/
    ├── ds/
    │   └── components.md                       # used in, Status (по решениям)
    └── tasks/
        ├── <TASK-ID>/analysis/
        │   └── screens-audit-<YYYY-MM-DD>.md   # полный отчёт прогона
        └── <любая задача>/artifacts/design/screens/<name>.md
                                                # «Edge cases — осознанно пропущены»
```

`ds/` означает `workspace/product/ds/`. Отчёт аудита — рабочий материал текущей задачи, поэтому лежит в её `analysis/`. Composition maps других задач дописываются только разделом с решениями пользователя, остальное не трогается.
Корневые `CLAUDE.md` и `AGENTS.md` не меняются.
